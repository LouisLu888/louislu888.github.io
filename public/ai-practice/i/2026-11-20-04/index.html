搭了四套 AI 系统后，他说人只该盯红灯

陈然复盘一年里为四类业务搭的 AI 系统，认为流程外壳只需四到六个交接节点，人按例外管理；重活放在本地包月订阅上跑，他估算比全部走云端 API 省下十到三十倍的月账单。

谁说的
陈然在旧金山工作，过去一年为外部交付门户、外联 CRM、个人常驻代理和多站点内容运营四类真实业务分别搭了 AI 系统，2026 年 11 月在个人网站上写了这篇复盘。
核心观点
他认为 AI 自己不需要看板，看板是给人掌控用的。所以流程分两层：外层是很简单的状态机，只放跨角色交接和确定性门禁；里面交给 Markdown Runbook 处理各种例外。人像塔台一样只看红灯：等自己拍板的、门禁失败或超时的、卡在客户那里的。
依据
依据是他的外联 CRM 实践：把模型调用拆成带提示词版本和 JSON Schema 的任务单，大批量粗活交给本地常开机器上的包月订阅，无风险的结果自动采纳，有异常标记的交给强模型和人复核，几乎不花按次 API 费用。
对你的意义
把手上一个 AI 流程压缩成四到六个阶段，只标出谁交给谁、哪一步要人放行；再把核心查询和写操作逐步封装成 MCP 接口。
争议·条件
这是他个人的判断（2026-11-20），他预计底层运行时 2027 年能到可用水平；本地订阅方案依赖常开机器和订阅额度。

陈然在这篇文章里说，他现在同时维护着四套互不连通的待办表、三套本机执行桥和三套发布保护机制，每次想合并都卡住。他总结出四个痛点：Agent 跑起来就听不见新指令，前台交付和后台协作脱节，云端 API 太贵，几套 SaaS 互相拼接。

可以直接借鉴的是两条原则。一是状态机只管交接点，例外交给 Runbook，避免把业务拆成几十个节点、最后谁也维护不动。二是按变化速度分层：调规则、改提示词、改审批阈值都当作带版本号的数据来更新，正在跑的任务锁定启动时的版本，新任务用新版本，不用重启。

他对 2027 年的判断是：中途转向、耐用租约这类通用的底层管道大概率会有成熟的开源方案，现在自己从零搭性价比很低；但业务口径、多角色可见性和人机授权的红线，没有框架能替你定，现在就该开始整理。
