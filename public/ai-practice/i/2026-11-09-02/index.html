遛狗时冒出一个问题，Claude 跑完了 C 和 Rust 的对比

Simon Willison 只用普通的 Claude 聊天，让它对比 C 和 Rust 写的 SQLite 扩展。改写之后，C 版在小数数据上从每行 106 ns 降到 18 ns。

谁·场景
Simon Willison 遛狗时好奇：写一个 SQLite 扩展函数 parse_number()，把「-$1,234.56」「12.5%」这类字符串转成数字，用 C 和用 Rust 各有多难？
怎么用
他在 Claude 聊天（Opus 5.5）里说明函数规则，要求比较两种语言的性能、代码复杂度和编译产物大小；发现 C 版偏慢后，又让它自己写解析函数追上 Rust；最后让它克隆他的 research 仓库，按已有格式写成报告并打包成 zip。
结果
第一轮结果：Rust 扩展 298–321 KB，C 扩展只有 14 KB，但 Rust 更快，原因是 Rust 里对应 strtod 的函数快一倍。改用 Clinger's fast path 后，在 200 万行混合数据上，C 版每行从 67 ns 降到 19 ns，Rust 两个版本分别是 46 ns 和 41 ns。
你可以试
手头有「A 和 B 哪个好」的技术问题时，先让聊天模型写原型、跑基准，再顺着结果追问为什么。最后让它按你已有的文档格式整理成报告。
注意
这类探索适合边界清楚的小问题。基准数字是模型在沙箱里跑出来的，要用到生产环境，还得在自己的机器和数据上重跑一遍。

Simon Willison 在研究笔记里记下了全过程，一共三条提示词：第一条提问题，第二条追问性能，第三条让模型照他 research 仓库的格式写报告。中间最有价值的是第二步：数据显示 C 版反而慢，他没有接受这个结论，而是让模型解释原因，再给它一个明确的目标：写一个能追上 Rust 的 C 解析器。小数数据上，C 版从 106 ns 降到 18 ns。

同一天他还在 Hacker News 评论里做了另一个小实验：在同一个对话里，让 Claude 把一个 77KB 的 Three.js 3D 作品改写成不依赖库的原生 JS，得到 98KB 的版本。两版看上去不完全一样，他说自己也没完全弄懂差异从哪来。

对工程师、PM 和做技术选型的人，这种用法可以用来低成本地预调研：开会讨论之前，先让模型拿出带数字的对比，人再判断哪些结果可信、哪些需要复核。
