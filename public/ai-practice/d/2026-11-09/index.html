AI 写的 PR 只留一段人话在外面，遛狗时让 Claude 跑完 C 和 Rust 的性能对比

01｜AI 写的 PR 说明太长，他只留一段人话在外面

谁·场景
开发者 Simon Willison 维护 Datasette、llm 等开源项目。他说自己现在的改动大多以 PR 的形式出现，由 Claude Code 或 Codex 替他开。
怎么用
PR 开头放一段人工确认过的高层说明，常配一张截图；智能体写的完整说明放进 <details><summary> 折叠块，summary 一栏写模型名和推理档位，例如「Claude Opus 5.5 Medium」。
结果
他说 PR 读起来不再像 slop。信息一点没少，读者扫一眼开头就能判断要不要细看。他贴了 5 个近期 PR 的开头段作为示例。
你可以试
下一份 AI 生成的 PR、周报或方案，先写两三句给人看的摘要，把长文折叠起来。GitHub 的 Markdown 直接支持这组标签，issue 评论里也能用。
注意
开头那段必须真的代表你的判断。可以从智能体原文里挑一句，但要你确认过。手机键盘敲这组标签很麻烦，GitHub 编辑器也没有对应按钮。

Simon Willison 在博客里说，现在的编码智能体写 PR 说明写得太好了：问题、方案、验证步骤一应俱全，也正因为太全，别人一看就知道是 AI 写的，第一反应是「我不读」。他自己就是这么想的，哪怕作者是他本人。

他的解法成本很低：一段人话开头＋截图＋折叠起来的 AI 全文。比如 Datasette 一个 PR 的开头只写了一句：行页面原来把单行显示成一行宽表，46 列的表会一路滚到右边，页面左边大片空白。另一个写的是 edit-tools.js（约 220KB）原来每个页面都加载，现在只在有编辑权限的用户第一次碰到编辑功能时才加载。summary 里标明模型名，读者一眼就知道折叠的部分是谁写的。

这个办法不只适用于代码。团队里谁的 AI 产出越多，读的人负担就越重。先用人的判断交代「为什么值得看」，细节留给需要的人展开，这条思路放到需求文档、调研报告、周报上都成立。他还给了一个记标签顺序的办法：读作「details-summary」，两个音节在前，三个音节在后。

02｜遛狗时冒出一个问题，Claude 跑完了 C 和 Rust 的对比

谁·场景
Simon Willison 遛狗时好奇：写一个 SQLite 扩展函数 parse_number()，把「-$1,234.56」「12.5%」这类字符串转成数字，用 C 和用 Rust 各有多难？
怎么用
他在 Claude 聊天（Opus 5.5）里说明函数规则，要求比较两种语言的性能、代码复杂度和编译产物大小；发现 C 版偏慢后，又让它自己写解析函数追上 Rust；最后让它克隆他的 research 仓库，按已有格式写成报告并打包成 zip。
结果
第一轮结果：Rust 扩展 298–321 KB，C 扩展只有 14 KB，但 Rust 更快，原因是 Rust 里对应 strtod 的函数快一倍。改用 Clinger's fast path 后，在 200 万行混合数据上，C 版每行从 67 ns 降到 19 ns，Rust 两个版本分别是 46 ns 和 41 ns。
你可以试
手头有「A 和 B 哪个好」的技术问题时，先让聊天模型写原型、跑基准，再顺着结果追问为什么。最后让它按你已有的文档格式整理成报告。
注意
这类探索适合边界清楚的小问题。基准数字是模型在沙箱里跑出来的，要用到生产环境，还得在自己的机器和数据上重跑一遍。

Simon Willison 在研究笔记里记下了全过程，一共三条提示词：第一条提问题，第二条追问性能，第三条让模型照他 research 仓库的格式写报告。中间最有价值的是第二步：数据显示 C 版反而慢，他没有接受这个结论，而是让模型解释原因，再给它一个明确的目标：写一个能追上 Rust 的 C 解析器。小数数据上，C 版从 106 ns 降到 18 ns。

同一天他还在 Hacker News 评论里做了另一个小实验：在同一个对话里，让 Claude 把一个 77KB 的 Three.js 3D 作品改写成不依赖库的原生 JS，得到 98KB 的版本。两版看上去不完全一样，他说自己也没完全弄懂差异从哪来。

对工程师、PM 和做技术选型的人，这种用法可以用来低成本地预调研：开会讨论之前，先让模型拿出带数字的对比，人再判断哪些结果可信、哪些需要复核。

03｜斯坦福 AI 编程课改作业：交给开源维护者审

谁说的
Mihail Eric 在斯坦福教 CS146S「The Modern Software Developer」，同时是 Monaco 的 AI 负责人。他上了 Latent Space 的节目。
核心观点
他认为功能实现可以交给智能体，人难以替代的部分是弄清维护者要不要这个改动、代码为什么这样写、补丁会弄坏什么。工具上他的原则是：「You buy to learn, and you build to keep.」
依据
他调查过的斯坦福大二、大三学生全都在用智能体写代码。节目引用 Faros 的研究：AI 采用度高的团队合并的 PR 多了 98%，PR 审查时间却长了 91%。
对你的意义
让智能体写完一个补丁后，用 Geoffrey Litt 的 explain-diff skill 生成讲解和测验，看哪道题你得回去翻代码才答得上，那里就是你还没真正理解的地方。
争议·条件
Monaco 自建工作区，是因为细节取决于它自己的云环境。对多数小团队来说，先买现成工具更合适。他预测开源仓库会变成由智能体运行的软件工厂，这是他个人的判断。

在 Latent Space 这期节目里，Mihail Eric 讲了课程第二轮的改动。第一轮的作业里有一项是让学生用 AI 审查工具审一个仓库并评估反馈，他判断这类练习学生现在一次提示就能做完。所以今年改成给真实的开源项目提补丁，由维护者审核。智能体一个下午就能写完功能，但维护者想不想要这个功能、这段代码为什么这样写，只能靠和人沟通才能弄清。这样的沟通，也是初级工程师向资深工程师学习的机会。

在 Monaco，团队评估了几款代码审查产品，最后留下了 Devin。智能体工作区则是自己搭的，因为后台智能体需要一个能运行产品、复现故障、测试补丁的环境，而这和公司的云配置绑在一起。内部系统 Hal 两类人都在用：工程师让它排查故障、开 PR，销售问它产品怎么运作，拿到的是能转述给客户的解释。

上面 98% 和 91% 那组数字说明，产出变快以后，瓶颈转到了审查和理解上。团队在加大 AI 编码投入之前，值得先想清楚谁来审、凭什么审。

04｜Box CEO：每三到六个月，把做不成的事再试一遍

谁说的
Box CEO Aaron Levie 在 X 上连发两帖；Codex 产品负责人、前 Linear 产品负责人 Nan Yu 同一天发了一条短帖。
核心观点
Levie 认为：每过三到六个月，都应该回头重试以前做不成的事；智能体能调用现有的系统和工具；多个智能体并行处理任务以后，效率提升不再局限在 20%–50%。
依据
他的依据是近六个月模型在电脑和工具使用、上下文衰减（context rot）、推理和多模态上的进步，并举编码领域已经出现的变化为例。安全、科研方向是他的推测。
对你的意义
把过去试过、失败了的 AI 任务记成一张清单，写上失败原因，每季度拿新模型重跑一遍。
争议·条件
Nan Yu 说，AI 让软件对「知道要做什么」的人更容易了，对不知道的人更难了：以前什么也做不出来，现在会花一大笔钱做出一堆垃圾。

Aaron Levie 2026-11-08 发帖说，AI 领域一条好经验是每三到六个月回头试一次以前做不成的事。他列举了过去半年模型在工具调用、长上下文和推理上的进步，认为凡是有 API 的系统，智能体都能调用。几小时后他在另一帖里进一步说，工作方式正从「和 AI 一来一回聊天」转向「给一组智能体布置问题，让它们并行干大量的活」，投入的时间和产出的关联会被打破。这些都是他的判断，编码领域是他举出的已有例子。

反方的提醒来自 Nan Yu：目标清楚的人可以直奔结果，不清楚的人会花钱做出一堆垃圾。两种说法放在一起看，能放大多少算力，取决于你能把问题说得多清楚。在把任务分给多个智能体之前，先把验收标准写出来。

05｜没写过 Swift 的创始人，用 Codex 做出挪威语口语 App

谁·场景
William Imoh 是开发者营销公司 Hackmamba 的创始人，团队约 25 人。他从迪拜搬到挪威，化工专业出身，自学编程，做过四年 PM，此前从没写过 Swift。
怎么用
他用 Codex 写原生的 iOS 和 Android 客户端，用 GPT-Live 做实时语音对话。经营公司这边，他在 Grok Bot 里给每个职能分配一个《指环王》角色。
结果
他在 How I AI 节目里现场演示了一段挪威语对话。Mural 已在 GitHub 开源。
你可以试
如果你也有一个用了很久、却没帮你解决真正问题的 App，可以先用实时语音模型做一个只覆盖核心场景的原型，自己天天用一段时间再说。
注意
语音陪练的体验取决于延迟，每次会话也有模型成本，他在节目里专门谈了这两点。上架和后续维护仍然需要你自己投入。

Claire Vo 在 How I AI 这期请来 William Imoh。他的出发点很直接：Duolingo 连续打卡 1000 天，还是没法用挪威语对话。他没写过 Swift，就用 Codex 做了原生的 Mural，语音部分接 GPT-Live。节目里还讲了让 App 界面和其他语言 App 区别开的那条设计提示词，以及每次会话的成本和语音陪练能接受的延迟上限。

另一半内容是他怎么一个人带约 25 人的公司：在 Grok Bot 里给每个创始人职能分配一个指环王角色，让智能体访问他 15 个常开的标签页，只保留一样不给。他说最让他担心的是对 AI 的依赖，被替代反倒不是。

对想做 AI App 的人，可以借鉴的是选题来自自己长期没解决的痛点，先自己当用户。源码可以直接参考。

今天可以做的一件事

今天挑一份你用 AI 生成、准备发给别人的长文档，比如 PR、周报或方案。先在开头写三句话：改了什么、为什么、需要对方看哪里，再把 AI 写的全文折叠起来或放进附录，模型名标在旁边。发出后记两件事：对方多久回复，追问的是开头那几句，还是折叠部分的细节。连做三次，你就能看出哪些信息该由你亲自把关，哪些可以交给 AI。
